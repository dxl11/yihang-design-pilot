# Web Design Brief

## 定位

将原始业务与用户材料转化为**可交接、可验证**的 Web Design Brief。

本 Skill **是**：需求澄清、目标分层、范围与风险识别、成功标准草案。  
本 Skill **不是**：Sitemap 定稿、视觉方向、完整用户研究报告、或编造调研数据。

## 触发场景

- 「帮我整理官网需求 / 写 design brief」。  
- 开工前材料混乱，需要先锁范围。  
- 后续要做 IA / 视觉方向，但缺少结构化简报。

## 不适用场景

- 用户只要改一页文案或修 bug。  
- 已有经确认的完整 Brief 且仅需微调视觉。  
- 非 Web 交付（纯 PPT / 品牌手册 → 用对应品类 Skill）。

## 输入要求

| 输入 | 必填 | 说明 |
|---|---|---|
| 项目/产品是什么 | 是 | 可粗糙 |
| 建站或改版目标 | 是 | 至少一句 |
| 目标用户线索 | 建议 | 缺失则标假设 |
| 现有站 / 竞品 / 品牌 / 内容清单 | 否 | 有则优先用原始材料 |
| 技术/时间/法务约束 | 否 | |

**原始材料优先于已整理摘要**：产品页、截图、功能列表、访谈摘录、反馈原文、分析数据导出。  
缺非关键字段**不终止**；缺「是什么 + 为何做」则最多追问一轮（≤3 问），否则写假设后继续并降置信度。

### 可信度标记（强制）

| 标记 | 含义 |
|---|---|
| `FACT` | 用户或可核对来源给出的事实 |
| `SOURCE` | 外部页面/文档摘录（注明出处） |
| `INFER` | 专业推断 |
| `HYPOTHESIS` | 未验证假设 |
| `TODO` | 待用户确认 |

禁止把 `HYPOTHESIS` 写成已验证用户研究结论。

## 任务理解（资深人员会多做的事）

普通 AI 常直接列「目标用户=年轻人」并开写。  
资深做法额外要求：

1. 拆开**商业目标 / 用户目标 / 网站目标**，找冲突。  
2. 问：缺了什么证据仍敢定范围？  
3. 把「想要一个高级官网」翻译成可观察结果或标为模糊需求。  
4. 明确**不做清单**，防止范围膨胀。  
5. 记录决策依赖（例如：定价未定 → 价格页策略待定）。

细则见 [methodology.md](references/methodology.md)。

## 执行流程

### Step 1 · 项目背景识别

判定：网站类型（营销官网 / 落地页 / 内容站 / 混合）、业务模式、产品成熟度、阶段（从 0 / 改版 / 合并站）。

### Step 2 · 目标与问题分析

分别列出商业 / 用户 / 网站目标；当前业务问题；设计应解决的问题；目标冲突表。

### Step 3 · 目标用户分析

群体、场景、任务、痛点、决策因素。无研究材料 → 仅 `HYPOTHESIS` 人物线索，禁止捏造引用与数据。

### Step 4 · 竞品与参考（可选）

有 URL/截图/名单时分析：定位、信息组织、转化策略——**借策略不抄皮**。无材料则写 `TODO`，不伪造浏览结果。

### Step 5 · 需求与约束

功能 / 内容 / 页面 / 品牌 / 技术 / 无障碍 / 性能 / 响应式 / 时间预算。区分 must / should / later。

### Step 6 · 成功标准

尽量可观察（注册、咨询提交、关键路径完成）。无数据时给建议指标并标 `TODO`。

### Step 7 · 风险与未知项

信息缺口、高风险假设、决策依赖、待确认问题列表（给用户勾选）。

### Step 8 · 生成 Brief 文件

写入用户项目（默认路径见下）。向用户展示「待确认事项」；重大范围冲突时停下等待确认。

## 工具调用

| 能力 | 用法 |
|---|---|
| Read / 搜索 | 读用户仓库、已有 md、公开资料 |
| 浏览器（若有） | 核实现有站/竞品；失败则记录限制 |
| 无工具 | 仅基于用户粘贴材料；标明未核验 |

**禁止**：伪造「已完成用户访谈 / 热力图 / A/B」等。

## 输出要求

默认写入用户项目：

```text
design-output/01-design-brief.md
```

若用户指定其他目录，遵守用户约定并在回复中声明路径。

必需章节见 [output-schema.md](references/output-schema.md)。摘要清单：

1. 项目概述  
2. 商业背景  
3. 业务目标  
4. 用户目标  
5. 目标用户  
6. 用户场景与任务  
7. 核心问题  
8. 网站目标  
9. 功能需求  
10. 内容需求  
11. 竞品与参考  
12. 成功指标  
13. 技术与设计约束  
14. 风险与假设  
15. 待确认事项  
16. 设计范围（含不做）  
17. 后续 Skill 建议（IA / 视觉方向等）

每条关键结论尽量带可信度标记。

## 质量检查（红线）

见 [quality-checklist.md](references/quality-checklist.md)。不满足则不得宣称 Brief 完成：

- [ ] 商业目标与网站目标已区分  
- [ ] 至少一条主用户任务可陈述  
- [ ] 假设均已标记  
- [ ] 有明确范围与不做清单  
- [ ] 有待确认事项（允许为空但须声明「无」）  
- [ ] 可被 IA / 视觉方向直接引用，无需再猜「网站要干什么」

## 失败处理

| 情况 | 处理 |
|---|---|
| 只有「做个好看的官网」 | 追问一轮；仍无则假设+低置信度 Brief，并阻断「假装需求充分」 |
| 材料互相矛盾 | 列出冲突，请用户裁定后再定范围 |
| 用户要立刻出视觉 | 可并行建议，但 Brief 文件仍须先落盘或同步落盘 |
